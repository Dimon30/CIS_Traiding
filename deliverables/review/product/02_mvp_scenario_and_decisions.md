# 2. MVP, сценарий и принятые решения

## Что реализовано

MVP включает пять направлений RUB→TJS/UZS/KGS/AMD/KZT, воспроизводимый data-to-signal pipeline на курсах ЦБ РФ, объяснимый ML-score, policy редких уведомлений и интерактивный React-прототип. В прототипе календарь читает сохранённые out-of-time сигналы; frontend не вычисляет модель и не парсит experiment CSV напрямую.

Не входят в MVP: банковские курсы и комиссии, персональные данные, персонализация, реальная доставка push и измерение конверсии. Поэтому MVP доказывает качество сигнала на рынке, а не финансовый эффект для клиента.

## Основной пользовательский сценарий

1. На новой дате система строит признаки только из доступной истории и находит кандидата.
2. Policy применяет corridor threshold, исключает повтор неизменившегося курса и cooldown 3 дня.
3. Клиент получает короткий push с наблюдаемым фактом, а не прогнозом.
4. По нажатию открывается экран перевода с актуальными условиями и контекстом сигнала.
5. Клиент сам подтверждает перевод или возвращается позже.

Если курс успел измениться, экран не поддерживает старое обещание: показывает актуальные условия, время push и нейтральное сообщение об изменении. Это решение защищает доверие и не требует фиксации курса.

## Ключевые решения → техническая реализация

| Решение AI Product | Техническое следствие |
|---|---|
| Ложный push дороже пропуска | Отбор редких пороговых сигналов и оценка safety/regret, а не оптимизация кликов |
| Сигнал не обещает идеальное дно | Target `message_hit`, h=3, epsilon=50 б.п. |
| Пользователя нельзя перегружать | Cooldown 3 календарных дня; неизменившиеся курсы не создают новый push |
| Нельзя подсматривать в будущее | Point-in-time признаки, purge gap и walk-forward test |
| Уведомление должно быть честным | Контролируемые шаблоны, актуализация условий на экране перевода |

Демо запускается из `fx-push-demo/`; данные его календаря экспортируются отдельным скриптом из явно выбранной OOT policy.
